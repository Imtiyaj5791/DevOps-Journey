# Kubernetes Day 3 — PV/PVC, RBAC, Networking & Ingress

## 1. Persistent Volumes (PV) and Persistent Volume Claims (PVC)

### Why do we need persistent storage?

A container's writable filesystem is not reliable for application data because the Pod/container can be recreated.

Kubernetes provides persistent storage using **PV and PVC**.

### PV

A **PersistentVolume (PV)** is a cluster-level storage resource.

```
Check PV:
kubectl get pv

Check PVCs:
kubectl get pvc -n <namespace>

Detailed PV:
kubectl get pvc -n <namespace>

Detailed PVc:
kubectl describe pv <pv-name>

pv.yml

apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  hostPath:
    path: /mnt/data
```


### PVC

A **PersistentVolumeClaim (PVC)** is a request for storage made by an application.

### Basic flow

```text
Storage
   ↓
PersistentVolume (PV)
   ↓
PersistentVolumeClaim (PVC)
   ↓
Pod
```
```
pvc.yml

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
  namespace: nginx-ns
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi

Inside the dep.yml file

inside the pod:

volumeMounts:
  - name: app-storage
    mountPath: /usr/share/nginx/html

volumes:
  - name: app-storage
    persistentVolumeClaim:
      claimName: my-pvc
```

### Interview answer

**Q: What is the difference between PV and PVC?**

**Answer:**
> A PersistentVolume is the actual storage resource available in the cluster, while a PersistentVolumeClaim is a request for storage made by a workload. The Pod uses the PVC to access the storage.

### Dynamic provisioning

```text
Pod
 ↓
PVC
 ↓
StorageClass
 ↓
Provisioner
 ↓
PV
```

Dynamic provisioning can automatically provision the required storage.

### Key points

- PV = storage resource
- PVC = storage request
- StorageClass = defines a class of storage and is commonly used for dynamic provisioning
- Pod mounts the PVC

# 2. RBAC

RBAC stands for **Role-Based Access Control**.

It controls **who can perform which actions on which Kubernetes resources**.

### Main RBAC objects

```text
Role
RoleBinding

ClusterRole
ClusterRoleBinding
```

### Role

A **Role** defines permissions within a specific namespace.

### RoleBinding

RoleBinding assigns a Role to an identity such as a User, Group, or ServiceAccount.

```text
Role
  ↓
RoleBinding
  ↓
User / ServiceAccount
```

### ClusterRole

ClusterRole defines permissions that can be used at cluster scope or reused across namespaces.

### ClusterRoleBinding

ClusterRoleBinding grants the associated ClusterRole at cluster scope.

### Common permissions

```text
get
list
watch
create
update
patch
delete
```
```
rback.yml

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

kubectl apply -f role.yml
kubectl get role -n dev


rolebinding.yml

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: nginx-ns
subjects:
  - kind: ServiceAccount
    name: developer
    namespace: nginx-ns
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

kubectl apply -f rolebinding.yml
kubectl get rolebinding -n dev

```
```
Check role:
kubectl get role -n <namespace>

Describe role:
kubectl describe role <role-name> -n <namespace>

Check rolebinding:
kubectl get rolebinding -n <namespace>

Describe rolebinding:
kubectl describe rolebinding <binding-name> -n <namespace>

Check ClusterRoles:
kubectl get clusterrole

Describe cluster role
kubectl describe clusterrole <role-name>

Check ClusterRoleBinding:
kubectl get clusterrolebinding

Describe:
kubectl describe clusterrolebinding <binding-name>


Check permission:
kubectl auth can-i get pods/delete -n dev

```

### Namespace vs Cluster scope

| Object | Scope |
|---|---|
| Role | Namespace |
| RoleBinding | Namespace |
| ClusterRole | Cluster / reusable across namespaces |
| ClusterRoleBinding | Cluster |

### Interview answers

**Q: What is RBAC in Kubernetes?**

**Answer:**
> RBAC is used to control access to Kubernetes resources based on roles. It defines which identities can perform actions such as get, list, create, update, or delete on specific resources.

**Q: Role vs ClusterRole?**

**Answer:**
> A Role is namespace-scoped, while a ClusterRole can define cluster-scoped permissions and can also be used with a RoleBinding for access within a namespace.

**Q: RoleBinding vs ClusterRoleBinding?**

**Answer:**
> RoleBinding grants permissions within a namespace, while ClusterRoleBinding grants the associated ClusterRole at cluster scope.

# 3. Kubernetes Networking

Kubernetes networking allows communication between Pods, Services, and external clients.

### Main communication types

```text
Pod → Pod
Pod → Service
External Client → Service
External Client → Ingress → Service → Pod
```

### Service

A Service provides a stable network endpoint for a group of Pods.

Pod IPs can change when Pods are recreated, so clients should normally communicate through a Service rather than directly using Pod IPs.

### Service types

```text
ClusterIP
NodePort
LoadBalancer
```

### ClusterIP

Default Service type. It is normally accessible only inside the cluster.

```text
Client/Pod
   ↓
ClusterIP Service
   ↓
Backend Pods
```

### NodePort

Exposes a Service through a port on each Kubernetes node.

```text
External Client
      ↓
NodeIP:NodePort
      ↓
Service
      ↓
Pods
```

### LoadBalancer

Used to expose a Service through an external load balancer, commonly in cloud environments.

### Interview answers

**Q: Why do we need a Kubernetes Service?**

**Answer:**
> A Service provides a stable IP address and DNS name for a group of Pods. It also provides load balancing across the matching Pods.

**Q: ClusterIP vs NodePort?**

**Answer:**
> ClusterIP is normally accessible only inside the cluster, while NodePort exposes the Service through a port on the Kubernetes nodes.

# 4. Ingress

## Why do we need Ingress?

Suppose we have multiple applications:

```text
frontend-service
backend-service
payment-service
```

Using separate NodePorts for every application can become difficult to manage.

Ingress allows HTTP/HTTPS traffic to be routed using host or path rules.

### Example

```text
example.com/
      ↓
frontend-service

example.com/api
      ↓
backend-service
```

## What is Ingress?

**Ingress is a Kubernetes API object used to define HTTP/HTTPS routing rules for external traffic.**

Important:

> Ingress defines the routing rules. The Ingress Controller actually implements those rules and handles the traffic.

### Host-based routing

```text
app.example.com
       ↓
frontend-service

api.example.com
       ↓
backend-service
```

### Path-based routing

```text
example.com/app
       ↓
frontend-service

example.com/api
       ↓
backend-service
```

### Interview answer

**Q: What is Ingress in Kubernetes?**

**Answer:**
> Ingress is a Kubernetes API object that defines HTTP/HTTPS routing rules. It can route traffic to different Services based on the hostname or URL path.

# 5. Ingress vs Service

| Service | Ingress |
|---|---|
| Provides a stable endpoint for Pods | Defines HTTP/HTTPS routing rules |
| Provides service discovery | Provides host/path-based routing |
| Can use ClusterIP, NodePort, LoadBalancer | Mainly used for HTTP/HTTPS |
| Routes traffic to Pods | Routes traffic to Services |

### Architecture

```text
Client
  ↓
Ingress Controller
  ↓
Ingress Rules
  ↓
Service
  ↓
Pod
```
```
Install Ingress controller

kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml

Check Controller pods
kubectl get pods -n ingress-nginx

Check IngressClass
kubectl get ingressclass

Check Controleer service
kubectl get svc -n ingress-nginx

ingress.yml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress
  namespace: nginx-ns
spec:
  ingressClassName: nginx
  rules:
    - host: nginx.local
      http:
        paths:
          - path: /app
            pathType: Prefix
            backend:
              service:
                name: nginx-service
                port:
                  number: 80

apply:- kubectl apply -f nginx-ingress.yml
Check:- kubectl get ingress -n nginx-ns
Describe:- kubectl describe ingress nginx-ingress -n nginx-ns
port forward:- kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80
Test:- curl -H "Host: nginx.local" http://127.0.0.1:8080

### Interview answer

**Q: Does Ingress replace Service?**

**Answer:**
> No. Ingress does not replace a Service. Ingress routes HTTP/HTTPS traffic to a Service, and the Service forwards the traffic to the appropriate Pods.

# 6. Ingress Controller

An **Ingress Controller** is the component that actually processes incoming traffic according to the Ingress rules.

Examples:

- NGINX Ingress Controller
- AWS Load Balancer Controller
- Traefik

### Important distinction

```text
Ingress
= What routing rules should be applied?

Ingress Controller
= How are those rules actually implemented?
```

### Interview answer

**Q: What is an Ingress Controller?**

**Answer:**
> An Ingress Controller is the implementation that watches Ingress resources and handles incoming traffic according to the configured routing rules.

# 9. Why did we use the existing Service?

Ingress does not normally send traffic directly to the Pod.

The normal flow is:

```text
Ingress
   ↓
Service
   ↓
Pod
```

Therefore our existing `nginx-service` was referenced in the Ingress:

```yaml
backend:
  service:
    name: nginx-service
    port:
      number: 80
```

### Interview answer

**Q: Why does Ingress use a Service instead of directly targeting a Pod?**

**Answer:**
> A Service provides a stable endpoint and selects the appropriate Pods. Ingress routes external HTTP/HTTPS traffic to that stable Service endpoint instead of depending on changing Pod IPs.

# 12. `/app` vs `/app/` — 301 Redirect

When we tested:

```bash
curl -H "Host: nginx.local" http://127.0.0.1:8080/app
```

NGINX returned:

```text
301 Moved Permanently
```

because `/app` is a directory and NGINX redirects it to:

```text
/app/
```

The direct request worked:

```bash
curl -H "Host: nginx.local" http://127.0.0.1:8080/app/
```

### Important point

This 301 was **NGINX directory behavior**, not an Ingress routing failure.

# 13. Important Interview Questions

### Q1. What is the difference between Ingress and Ingress Controller?

**Answer:**
> Ingress is the Kubernetes resource that defines routing rules. The Ingress Controller is the component that implements those rules and handles the incoming traffic.

### Q2. Can Ingress route traffic directly to a Pod?

**Answer:**
> Normally, Ingress routes traffic to a Kubernetes Service, and the Service forwards the traffic to the selected Pods.

### Q3. What type of traffic does Ingress mainly handle?

**Answer:**
> Ingress is mainly designed for HTTP and HTTPS traffic.

### Q4. What are host-based and path-based routing?

**Answer:**
> Host-based routing selects a backend based on the hostname, such as `api.example.com`. Path-based routing selects a backend based on the URL path, such as `/api`.

### Q5. Does Ingress replace NodePort or LoadBalancer?

**Answer:**
> Ingress provides an HTTP/HTTPS routing layer and can reduce the need to expose every application through separate NodePorts or LoadBalancer Services. It does not replace the Kubernetes Service itself.

### Q6. Why is `ingressClassName` used?

**Answer:**
> `ingressClassName` tells Kubernetes which Ingress Controller should handle the Ingress resource.

### Q7. What is `pathType: Prefix`?

**Answer:**
> Prefix matching routes requests whose path starts with the configured path. For example, `/app` can match `/app`, `/app/`, and paths below `/app`.

### Q8. What happens when a Pod behind a Service is recreated?

**Answer:**
> The Pod can get a new IP, but the Service continues to provide a stable endpoint and routes traffic to the currently matching Pods.

### Q9. Why do we need a Service if we already have Ingress?

**Answer:**
> Ingress provides external HTTP/HTTPS routing, while the Service provides a stable endpoint and Pod selection inside the cluster. The normal architecture is Ingress → Service → Pod.

### Q10. Explain the complete request flow.

**Answer:**
> A client sends an HTTP/HTTPS request to the Ingress endpoint. The Ingress Controller receives the request, checks the Ingress routing rules, forwards it to the matching Service, and the Service sends it to one of the selected Pods.
