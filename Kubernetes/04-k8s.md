# Rolling Update & Rollback

 A Rolling Update allows us to deploy a new application version gradually instead of stopping all existing pods at once, By default, Deployment uses RollingUpdate strategy.
 
 Rollback means reverting the Deployment to the previous stable version if the new version has an issue.
 
 maxSurge = how many extra pods can be created temporarily during the update.
 
 maxUnavailable = how many pods can be temporarily unavailable during the update.

```
Example:

Before:
3 Pods → v1

Update:
v1 → v2

After:
3 Pods → v2

This helps maintain application availability during deployment.

 How Rolling Update Works

Deployment manages the update through ReplicaSets.

Deployment
    ↓
New ReplicaSet
    ↓
New Pods
    ↓
Old ReplicaSet gradually scales down

Example:

Old ReplicaSet → nginx:1.25
New ReplicaSet → nginx:1.27

Kubernetes gradually replaces old pods with new pods.

Update Deployment Image
kubectl set image deployment/roll-dep nginx=nginx:1.27 -n roll-ns

Check Rollout Status
kubectl rollout status deployment/roll-dep -n roll-ns

Watch Rolling Update Live
kubectl get pods -n roll-ns -w

Deployment Revision History
kubectl rollout history deployment/roll-dep -n roll-ns

If the new version has an issue, we can return to the previous working revision.
kubectl rollout undo deployment/roll-dep -n roll-ns
```

# Deployment Strategies: 
A Deployment Strategy defines how a new version of an application is deployed and how traffic/users are moved from the old version to the new version.

### Recreate:-
Recreate stops all Pods running the old version before starting the new version, so it can cause downtime.

### Rolling Update:-
Rolling Update gradually replaces old Pods with new Pods without taking all Pods down at the same time.

### Blue/Green:- 
Blue/Green deployment runs the old and new versions separately and switches traffic to the new version after validation.

### Canary:- 
Canary deployment gradually exposes the new version to a small percentage of users or traffic before rolling it out to everyone.

## Important:

Kubernetes Deployment natively supports only Recreate and RollingUpdate.
Blue/Green and Canary are deployment patterns implemented using resources such as Deployments, Services, Ingress/controllers, or service mesh.

```
### Recreate Lab:-

apiVersion: apps/v1
kind: Deployment
metadata:
  name: recreate-dep
  namespace: roll-ns

spec:
  replicas: 3

# Horizontal Pod Autoscaler (HPA)

HPA automatically increases or decreases the number of Pods based on resource utilization or other configured metrics.
Horizontal scaling = increase or decrease the number of Pods.
Vertical scaling = increase or decrease the resources of pods.

```
Maually Increse: 

kubectl scale deployment myapp --replicas=5

To check metric server running in k8s :

kubectl get deployment metrics-server -n kube-system

To check CPU and memory usage for your Kubernetes nodes:-

kubectl top nodes

To check CPU and memory usage for your Kubernetes pods:-

kubectl top pods -n nginx-server

```

# Create a Deployment for HPA

```

HPA Lab:-

nano hpa-deployment.yml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hpa-demo
  namespace: nginx-ns

spec:
  replicas: 2

  selector:
    matchLabels:
      app: hpa-demo

  template:
    metadata:
      labels:
        app: hpa-demo

    spec:
      containers:
        - name: nginx
          image: nginx:1.25

          resources:
            requests:
              cpu: "100m"
            limits:
              cpu: "500m"

kubelctl apply -f dep.yml

nano hpa.yml

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: hpa-demo
  namespace: nginx-ns

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo

  minReplicas: 2
  maxReplicas: 5

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

kubectl apply -f hpa.yml 
kubectl get hpa -n nginx-ns

now create service:-

kubectl expose deployment hpa-demo \
  --name=hpa-demo-svc \
  --port=80 \
  --target-port=80 \
  -n nginx-ns


then create a pod for testing:- 

kubectl run load-generator \
  --image=busybox \
  -n nginx-ns \
  -- /bin/sh -c "while true; do wget -q -O- http://hpa-demo-svc; done"
```


# HELM

Helm is a package manager for Kubernetes that helps us package, template, install, upgrade, and manage Kubernetes resources as a reusable Chart.

### Install Helm:
```
sudo snap install helm --classic
```

To create chart/package/Template

helm create myapp
 
inside helpm chat 

myapp/
├── Chart.yaml 
├── values.yaml 
├── charts/
└── templates/

### Helm Install
```
helm install myapp ./myapp -n nginx-ns
helm list -n nginx-ns
kubectl get deployment,pods,svc -n nginx-ns
```
### Helm Upgrade
```
sed -i 's/replicaCount: 1/replicaCount: 3/' myapp/values.yaml
helm upgrade myapp ./myapp -n nginx-ns (pod 1 to 3)
helm history myapp -n nginx-ns
```
### Helm Rollback
```
helm rollback myapp 1 -n nginx-ns ( rollback v1 version)
helm status myapp -n nginx-ns
```
### Helm Image Upgrade
```
helm upgrade myapp ./myapp -n nginx-ns ( image 1.16 to 1.27) rolling update
Kubectl get deploy myapp -n nginx-ns -o wide
helm rollback myapp 4 -n nginx-ns ( rollback previous version)
```

### Override Values Using --set

```
helm upgrade myapp ./myapp -n nginx-ns --set replicaCount=2 ( without edit local chart value change the pod number)
```

### Import Existing Kubernetes YAML into Helm Chart
```
cp dep.yml myapp/templates/roll-deployment.yaml
ls myapp/templates/
helm template myapp ./myapp -n roll-ns
sed -i 's/replicas: 3/replicas: {{ .Values.replicaCount }}/' myapp/templates/roll-deployment.yaml
helm install rolltest ./myapp -n roll-ns
kubectl get deployment -n roll-ns
sed -i 's|image: nginx:1.25|image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"|' myapp/templates/roll-deployment.yaml
```

# Release:-
 A Release is a deployed instance of a Helm Chart.

#Helm is not a replacement for kubectl. For simple applications, kubectl apply is sufficient. Helm is useful when we want to package multiple Kubernetes resources into a reusable Chart and manage the application's configuration, installation, upgrades, and rollbacks consistently.



# Helm installation failed. How will you troubleshoot?
"If Helm installation fails, first I check the error message. Then I check helm status and helm history to understand the failure. After that, I validate the chart using helm lint and helm template. I fix the issue and retry the installation."

# Helm upgrade failed. How will you troubleshoot?
"If Helm upgrade fails, first I check the error message. Then I check helm status and helm history to identify the failed revision. I validate the chart using helm lint and check the generated manifest using helm template. If required, I rollback to the previous working revision and fix the issue."

# Helm release deployed successfully but Pods are not running. How will you troubleshoot?
"If Helm release is successful but Pods are not running, first I check the Pod status using kubectl get pods. Then I check the Pod details using kubectl describe pod and check logs using kubectl logs to find the root cause."

# How do you rollback a failed Helm deployment?
if a Helm deployment fails after an upgrade, first I check the release history using helm history. Then I identify the previous working revision and rollback using helm rollback."

# Difference between helm template and helm get manifest?
helm template is used before deployment to check what Kubernetes YAML will be generated from the Helm chart. helm get manifest is used after deployment to check what Kubernetes YAML was actually deployed by a Helm release."

# Difference between values.yaml and --set in Helm?
values.yaml is used to store default configuration values for a Helm chart. --set is used to override those values temporarily during helm install or upgrade.

# What happens if two users try to install the same Helm release name?
Helm does not allow the same release name in the same namespace. The second installation will fail because that release name already exists.

# How do you manage different environments (Dev/Test/Prod) using Helm?
We use the same Helm chart for different environments and maintain separate values files for each environment.

```
