## ConfigMap + Hands-on

ConfigMap is used to store non-sensitive configuration data separately from the application code or container image. We can pass ConfigMap values to the container as environment variables or mount them as files. I also created a ConfigMap and used it with my Nginx Deployment.

```
kind: ConfigMap
apiVersion: v1
metadata:
  name: nginx-config
  namespace: nginx-ns
data:
  APP_PORT: "8080"
  APP_ENV: dev
  DB_USERNAME: appuser
```
```
### Apply:
kubectl apply -f configmap.yml

### Check ConfigMap:
kubectl get configmap -n nginx-ns

### View ConfigMap details
kubectl describe configmap nginx-config -n nginx-ns
```
## Secrets + Hands-on

Secret is used to store sensitive information like passwords, tokens, API keys and credentials. We can use Secret values inside the Pod. I also created a Secret and used it in my Deployment.

```
kind: Secret
apiVersion: v1
metadata:
  name: nginx-secret
  namespace: nginx-ns

type: Opaque

data:
  DB_PASSWORD: QUJD
```

```
kubectl apply -f secret.yml
kubectl get secret -n nginx-ns
kubectl describe secret nginx-secret -n nginx-ns
```
## CPU/Memory Requests & Limits

Request tells the Scheduler how much resource the Pod needs for scheduling. It does not mean the application will always use that much resource.”

“Limit tells the maximum resource the container can use. If the container crosses the memory limit, it can be OOM-killed.

Example:

“If the request is 128Mi and the limit is 256Mi, Kubernetes considers 128Mi while scheduling, but the application can use more than 128Mi, up to 256Mi.”

## OOM Troubleshooting

First, I will check the Pod status using kubectl get pods. Then I will check the application logs using kubectl logs, and if the container has restarted, I will check the previous logs using --previous. After that, I will use kubectl describe pod to check the exact reason, events and container state. If it looks like a CPU or memory issue, I will use kubectl top pod. If the container is running and I need to investigate inside the container, I will use kubectl exec.

```
Check Pod:

kubectl get pods -n <namespace>

Check current logs:

kubectl logs <pod-name> -n <namespace>

Check previous container logs"

kubectl logs <pod-name> -n <namespace> --previous

Check Pod details/events:

kubectl describe pod <pod-name> -n <namespace>

Check Pod Resource Usage:

kubectl top pod <pod-name> -n <namespace>

Enter the container if required:

kubectl exec -it <pod-name> -n <namespace> -- sh
```

## Liveness Probe

Liveness probe checks whether the application inside the container is alive and healthy. If the application is not healthy and the probe continuously fails, Kubernetes restarts the container.

## Readiness Probe

Readiness probe checks whether the application is ready to receive traffic. If the probe fails, the Pod becomes NotReady and the Service stops sending traffic to that Pod. The container is not restarted

```
kind: Deployment
apiVersion: apps/v1
metadata:
  name: nginx-dep
  namespace: nginx-ns

spec:
  replicas: 2
  selector:
    matchLabels:
      env: dev
  template:
    metadata:
     labels:
      env: dev

    spec:
      containers:
         - name: nginx-pod
           image: nginx
           envFrom:
            - configMapRef:
                name: nginx-config
            - secretRef:
                name: nginx-secret
           resources:
              requests:
                cpu: "100m"
                memory: "128Mi"
              limits:
                cpu: "500m"
                memory: "256Mi"
           livenessProbe:
              httpGet:
                path: /
                port: 80
           readinessProbe:
              httpGet:

                path: /
                port: 80
```
